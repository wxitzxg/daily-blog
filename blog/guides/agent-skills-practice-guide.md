# Agent Skills 实战：把工作产出写成 Skill

团队协作中最常见的问题是：每个人写文档的方式都不一样，关键项经常缺失，评审难聚焦、对齐成本高。把团队模板写进一条 **Agent Skill**，当你说「写 PRD」「写路线图」「排一下需求优先级」时，助手会按同一套结构输出，必填节不遗漏、格式可追溯。

本文以 PRD 需求文档和产品经理常用产出为例，完整讲解如何将工作产出模板化为可复用的 Skill。

---

## 一、为什么需要自定义 Skill

### 解决的问题

- **结构不一**：同一类文档，不同人写出来结构差异大
- **关键项缺失**：评审时才发现缺少成功指标、验收标准等
- **对齐成本高**：每次都要重新解释「应该怎么写」
- **复用困难**：新人上手慢，团队知识难以沉淀

### Skill 的价值

把团队规范写成 Skill 后：

- 助手按固定结构输出，必填节不遗漏
- 团队成员拉代码即有一致模板
- 新人可通过触发 Skill 快速学习团队规范
- 文档评审有明确检查标准

### 核心方法论

```
把团队规范清单化 → SKILL.md → reference.md → 触发与协作
```

## 二、把 PRD 需求文档写成 Skill

### 2.1 定义 PRD 文档要素

先明确「写什么、怎么写」。PRD 常见要素：

| 要素 | 必填 | 建议 | 可选 |
| --- | --- | --- | --- |
| 背景与问题 | 是 | 问题陈述清晰、有数据或依据 | 竞品/市场参考 |
| 目标与成功指标 | 是 | 目标可衡量、指标可追踪 | 基线数据 |
| 用户与场景 | 视团队 | 目标用户、1～3 个核心场景 | 用户旅程图 |
| 功能需求 | 是 | 用户故事或需求列表、带优先级 | 与设计/工单关联 |
| 范围与边界 | 是 | 本期做/不做 明确 | 版本规划 |
| 验收标准 | 是 | 每条需求有可验证条件 | 测试用例链接 |
| 依赖与约束 | 视团队 | 关键依赖、上线时间/合规 | 风险列表 |

### 2.2 SKILL.md 结构

在 `.cursor/skills/prd-requirement/` 下建 `SKILL.md`，目录结构：

```
prd-requirement/
├── SKILL.md
├── reference.md   # 可选，完整 PRD 模板、需求书写规范、示例
└── scripts/       # 可选，检查 PRD 是否含必选节
    └── check-prd-sections.sh
```

**SKILL.md 示例**：

```markdown
---
name: prd-requirement
description: 按团队模板生成或评审 PRD（产品需求文档）；适用于用户说「写 PRD」「写需求文档」「生成产品需求」「按模板写 PRD」「审一下这份 PRD」或提及 PRD、需求文档时。
---

# PRD / 需求文档技能

当用户要求撰写或评审 PRD 时，按以下模板与规范生成一篇完整文档，或输出符合性检查结果。

## 执行前

- **输入范围**：用户提供的产品背景、目标、用户与场景、已有 PRD 草稿或片段。若用户只说「写一份 PRD」等未提供任何要点，先询问：产品/功能名称、要解决的问题、目标用户、核心目标或成功指标，再生成。
- 确认有至少**产品/功能主题与目标（或问题陈述）**后，再按下方模板输出；缺项用 `[请补充：xxx]` 占位。

## 文档结构（必填节）

按以下顺序输出，每节必须有内容或占位说明：

1. **背景与问题**：要解决什么问题、为谁、当前痛点或机会
2. **目标与成功指标**：业务/产品目标、可衡量的成功指标
3. **用户与场景**：目标用户、1～3 个核心使用场景
4. **功能需求**：用户故事（As a… I want… So that…）或需求列表，每条带 ID 与优先级
5. **范围与边界**：本期做啥（In scope）、明确不做啥（Out of scope）
6. **验收标准**：每条需求对应可验证的验收条件
7. **依赖与约束**（若适用）：关键依赖、上线时间、合规或性能约束

## 需求书写规范

- **用户故事**：角色 + 能力 + 价值，如「作为注册用户，我希望 能通过邮箱找回密码，以便在忘记密码时自助恢复」
- **需求列表**：每条可验收、无歧义；避免「优化体验」等不可验证表述，改为可观测结果
- **优先级**：P0 必须本期交付，P1 重要可下期，P2 可选

## 输出格式

- 输出为完整 **Markdown** 文档，可直接复制到文档系统
- 占位符统一为 `[请补充：xxx]` 或 `[待确认]`
```

### 2.3 reference.md 模板参考

若团队有固定 PRD 模板，可在同目录下增加 `reference.md`：

```markdown
# PRD 模板与需求书写参考

## 一、完整 PRD 模板（复制用）

\`\`\`markdown
# PRD：[产品/功能名称]

## 背景与问题
[要解决什么问题、为谁、当前痛点或机会]

## 目标与成功指标
- 目标：
- 成功指标：（可衡量，如转化率、留存、NPS）

## 用户与场景
- 目标用户：
- 核心场景：

## 功能需求
| ID | 描述（用户故事或需求） | 优先级 |
|----|------------------------|--------|
|    |                        | P0/P1/P2 |

## 范围与边界
- In scope：
- Out of scope：

## 验收标准
- 每条需求对应可验证条件

## 依赖与约束
- 依赖 / 时间 / 合规等
\`\`\`

## 二、用户故事与验收标准规范

### 用户故事
- 格式：**作为** [角色]，**我希望** [能力/行为]，**以便** [价值/目标]
- 一条故事只描述一个可交付能力

### 验收标准
- 格式：**Given** 前置条件 **When** 操作 **Then** 预期结果
- 每条需求至少一条可验证的验收条件

### 禁止表述
- 「优化体验」「提升性能」→ 改为可观测指标（如「首屏 < 2s」）
- 「尽量」「可能」→ 改为明确规则或列出例外
```

### 2.4 可选 scripts 辅助检查

`scripts/check-prd-sections.sh`（检查.md 是否含必选二级标题）：

```bash
#!/usr/bin/env bash
# 用法: ./scripts/check-prd-sections.sh <prd.md 路径>
# 输出缺失的必选节，供 prd-requirement 技能并入符合性检查。

FILE="${1:-}"
if [ -z "$FILE" ] || [ ! -f "$FILE" ]; then
  echo "Usage: $0 <path-to-prd.md>"
  exit 1
fi

echo "=== PRD 必选节检查 ==="
for section in 背景与问题 目标与成功指标 用户与场景 功能需求 范围与边界 验收标准; do
  if grep -qE "^## *$section" "$FILE" 2>/dev/null; then
    echo "✓ $section"
  else
    echo "✗ 缺失: $section"
  fi
done
```

## 三、把产品经理常用产出写成 Skill

### 3.1 定义文档类型与要素

产品经理常用产出可分为五类：

| 文档类型 | 必填项 | 建议项 | 可选 |
| --- | --- | --- | --- |
| 路线图 | 时间轴、主题/目标、里程碑 | 依赖与风险、战略对齐 | 资源/人力 |
| 需求优先级 | 优先级框架、排序列表、理由 | 与目标对齐 | 容量/工时 |
| 版本规划 | 版本目标、范围、时间 | 依赖与风险、发布节奏 | 回滚策略 |
| 竞品分析 | 竞品列表、对比维度、结论与行动 | 数据/截图来源 | 更新频率 |
| 产品汇报 | 周期、进展、下周重点 | 指标、阻塞、需决策项 | 干系人 |

**适用边界说明**：

| 需求场景 | 应选文档类型 | 典型输出 |
| --- | --- | --- |
| 规划季度/半年方向 | 路线图 | 时间轴 + 主题 + 里程碑 |
| 对候选需求排序 | 需求优先级 | 排序表 + 理由 |
| 安排某个版本范围 | 版本规划 | 版本目标 + 范围 + 发布节奏 |
| 对比市场方案 | 竞品分析 | 对比表 + 结论 + 行动 |
| 对上同步进展 | 产品汇报 | 进展 + 风险 + 下步 |

### 3.2 常见混淆辨析

- **路线图 vs 版本规划**：路线图回答「未来一段时间做什么方向」，强调阶段目标；版本规划回答「下个版本具体上什么」，强调范围和时间
- **需求优先级 vs 版本规划**：优先级用于排序「先做谁、为什么」；版本规划确定「这次实际上哪些会上线」
- **产品汇报 vs 项目周报**：产品汇报强调业务目标、指标进展、决策请求；项目周报更偏执行状态和任务推进

### 3.3 SKILL.md 结构

在 `.cursor/skills/pdm/` 下建 `SKILL.md`：

```
pdm/
├── SKILL.md
├── reference.md   # 可选，各类型完整模板、优先级框架说明
└── scripts/       # 可选，检查文档是否含必选节
    └── check-pdm-sections.sh
```

**SKILL.md 示例**：

```markdown
---
name: pdm
description: 按团队模板生成或评审产品经理常用文档，含产品路线图、需求优先级、版本规划、竞品分析、产品汇报等；适用于用户说「写路线图」「写版本规划」「排一下需求优先级」「写竞品分析」「写产品周报」等表达。
---

# 产品经理（PDM）文档技能

当用户要求撰写或评审产品经理常用文档时，先确认**文档类型**，再按该类型的模板与规范生成文档。

## 工作模式

- **生成模式**：输入为文档类型 + 零散素材，输出为按模板整理好的完整 Markdown 草稿
- **补全模式**：输入为半成品草稿，输出为补全后的版本
- **评审模式**：输入为已有文档，输出为符合项、缺项、必改项、建议项

## 执行前

- **文档类型判断**：
  - 「路线图」「roadmap」「Q2 做哪些方向」→ 路线图
  - 「优先级」「排需求」「backlog」→ 需求优先级
  - 「版本规划」「发布计划」「下个版本上什么」→ 版本规划
  - 「竞品分析」「竞品对比」→ 竞品分析
  - 「周报」「月报」「汇报」「给领导同步」→ 产品汇报
- 若无法判断，先询问用户要写哪一类

## 文档类型一：产品路线图

**必填节**：时间轴（如 Q1～Q4）、各阶段主题或目标、关键里程碑、依赖与风险

## 文档类型二：需求优先级 / Backlog 排序

**必填节**：采用的优先级框架（如 RICE、MoSCoW）、排序结果（需求 + 优先级 + 理由）、与目标对齐说明

## 文档类型三：版本规划 / 发布计划

**必填节**：版本号与目标发布时间、版本目标、范围（需求列表）、依赖与风险、发布节奏

## 文档类型四：竞品分析

**必填节**：竞品列表、对比维度（功能/体验/定价等）、结论与产品行动建议

## 文档类型五：产品汇报 / 周报

**必填节**：汇报周期、本周进展、核心指标、阻塞与风险、下周重点、需决策项

## 通用规范

- 占位符统一为 `[请补充：xxx]` 或 `[待确认]`
- 未由用户提供的信息，不要写成确定事实
- 规划类文档需显式写出依赖、风险、待确认项
- 评审已有文档时，只检查结构完整性，不擅自改写业务事实
```

### 3.5 可选 scripts 辅助检查

`scripts/check-pdm-sections.sh`：

```bash
#!/usr/bin/env bash
# 用法: ./scripts/check-pdm-sections.sh <文档.md 路径> <类型：roadmap|priority|release|competitor|report>

FILE="${1:-}"
TYPE="${2:-}"
if [ -z "$FILE" ] || [ ! -f "$FILE" ]; then
  echo "Usage: $0 <path-to-doc.md> <roadmap|priority|release|competitor|report>"
  exit 1
fi

case "$TYPE" in
  roadmap)   SECTIONS="时间轴 主题 目标 里程碑 依赖" ;;
  priority)  SECTIONS="优先级框架 排序 理由 目标对齐" ;;
  release)   SECTIONS="版本号 版本目标 范围 时间 依赖 发布" ;;
  competitor) SECTIONS="竞品 对比 结论 行动" ;;
  report)    SECTIONS="周期 进展 重点 决策" ;;
  *)         echo "Unknown type: $TYPE"; exit 1 ;;
esac

echo "=== PDM 文档必选节检查（$TYPE）==="
for section in $SECTIONS; do
  if grep -qE "^## *.*$section|^# *.*$section" "$FILE" 2>/dev/null; then
    echo "✓ 含相关节: $section"
  else
    echo "✗ 建议补充: $section"
  fi
done
```

## 四、最佳实践

### 4.1 触发方式

- **隐式触发**：用户说「写 PRD」「写路线图」「排一下需求优先级」等，助手根据 description 匹配到对应 Skill
- **显式触发**：用户说「用 prd-requirement 技能写一份 PRD」或输入 `/prd`（若产品支持）

### 4.2 输出规范

- 输出为 **可直接复制的完整 Markdown 文档**
- 缺项用 `[请补充：xxx]` 标出
- 评审模式输出为必改/建议/可选清单，每条带位置与修改建议

### 4.3 团队协作

- **统一技能目录**：把 Skill 放在项目内 `.cursor/skills/`，随仓库提交，团队成员拉代码即有一致模板
- **Review 他人写的 Skill**：新技能或改动可走 PR，重点看：
  - description 是否覆盖常见说法
  - 文档结构是否与团队共识一致
  - 书写规范是否清晰

### 4.4 Skill 合并策略

当多类文档有相似结构时，可合并为一条 Skill：

- PRD 和需求文档可合并为 `prd-requirement`
- 路线图、优先级、版本规划、竞品分析、汇报可合并为 `pdm`
- 合并后的 Skill 通过「文档类型判断」分支到不同模板

### 4.5 与其他 Skill 的关系

- **PRD vs PDM**：PRD 定「单次需求做什么」；PDM 侧重「排期、优先级、规划与汇报」
- 先有 PDM 的路线图和优先级排序，再有 PRD 定义具体需求
- 两者互补，覆盖产品经理从规划到落地的完整流程

---

## 总结

从团队规范到可复用的 Skill，核心步骤：

1. **定义文档要素**：明确必填项、建议项、可选项
2. **编写 SKILL.md**：description 覆盖常见表达 + 执行前检查 + 文档结构 + 书写规范
3. **补充 reference.md**：完整模板、框架说明、示例
4. **可选 scripts**：辅助检查必选节是否缺失
5. **团队协作**：统一目录、PR Review、持续迭代

这样完成的一条 Skill，既可用于生成草稿，也可用于符合性评审，帮助团队统一文档标准、降低沟通成本。
