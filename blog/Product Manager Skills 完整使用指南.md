## 1\. 总体概述

### 1.1 什么是 Product Manager Skills？

这是一套 **产品管理框架的数字化封装** ，包含 46 个独立但相互关联的技能（Skill），每个技能对应产品管理工作中的一个具体环节。

**核心理念** ：

> 用户不是买产品，而是"雇佣"产品来完成某项工作（Jobs-To-Be-Done）。

**设计目标** ：

- 📚 将经典产品管理方法论（JTBD、OST、精益 UX 等）转化为可执行的 AI 工作流
- 🔗 打通产品发现→定义→交付→验证的完整链条
- 🎯 避免"功能工厂"陷阱，确保团队解决正确的问题

### 1.2 与 JTBD 的关系

**JTBD (Jobs-To-Be-Done)** 是这套技能体系的 **核心思想基础** ：

```
JTBD 理论 → 理解用户"雇佣"产品完成的工作
    ↓
产品发现 → 搞清楚用户真正的需求是什么
    ↓
产品定义 → 决定做什么来解决这些需求
    ↓
产品交付 → 把解决方案做出来
    ↓
产品验证 → 检查是否真的解决了问题
```

这 46 个技能就是沿着这个链条展开的 **工具箱** 。

### 1.3 技能分类总览

| 类别 | 技能数量 | 核心用途 |
| --- | --- | --- |
| 📊 用户研究 | 5 个 | 理解用户、挖掘需求 |
| 📈 市场分析 | 6 个 | 评估机会、竞争分析 |
| 🎯 产品定义 | 8 个 | 问题定义、优先级决策 |
| 📝 文档输出 | 6 个 | PRD、用户故事、故事板 |
| 📋 战略规划 | 7 个 | 路线图、业务健康度 |
| 🎓 高阶能力 | 14 个 | 领导力、AI 能力、上下文工程 |

## 3\. 核心技能详解

### 3.1 jobs-to-be-done（用户待办任务）

**核心功能** ：系统性地探索用户真正想完成的工作，而非表面需求。

**解决的问题** ：

- 用户说的"想要更快"到底是什么意思？
- 为什么有些功能上线后数据没变化？
- 如何避免做错功能？

**输出结构** ：

```
## Jobs-to-be-Done 分析

### 1. Customer Jobs（用户想完成的事）
#### Functional Jobs（功能层面）:
- [任务 1]
- [任务 2]

#### Social Jobs（社会层面）:
- [用户希望被如何看待]

#### Emotional Jobs（情感层面）:
- [用户追求/避免的情感状态]

### 2. Pains（痛苦）
#### Challenges（障碍）:
- [障碍 1]

#### Costliness（代价）:
- [时间/金钱/精力成本]

#### Common Mistakes（常见错误）:
- [错误 1]

#### Unresolved Problems（未解决问题）:
- [现有方案未解决的问题]

### 3. Gains（收益）
#### Expectations（期待）:
- [超出期待的点]

#### Savings（节省）:
- [时间/金钱/精力节省]

#### Adoption Factors（采用因素）:
- [促使用户切换的因素]

#### Life Improvement（生活改善）:
- [用户生活如何变好]
```

**使用示例** ：

```
场景：老板说"用户想要更快的开票速度"

调用 jobs-to-be-done 后，你发现：
- 表面需求："更快开票"
- 真实 JTBD："从完工到收款的整个流程别耽误"
- 真正机会：自动催款 + 收款跟踪，而不是"一键开票"按钮
```

### 3.2 opportunity-solution-tree（机会方案树）

**核心功能** ：从模糊的需求到结构化的探索，避免"功能工厂"陷阱。

**解决的问题** ：

- 老板/客户直接说"我要这个功能"怎么办？
- 如何确保团队在解决问题，而不是盲目堆功能？
- 如何系统性地探索多种解决方案？

**输出结构** ：

```
期望结果 (Outcome)
                           │
           ┌───────────────┼───────────────┐
           │               │               │
      机会 1            机会 2          机会 3
    (问题/需求)        (问题/需求)      (问题/需求)
       │                 │               │
    ┌──┴──┐           ┌──┴──┐        ┌──┴──┐
    │     │           │     │        │     │
  方案 1 方案 2      方案 1 方案 2   方案 1 方案 2
    │     │           │     │        │     │
  实验  实验         实验  实验      实验  实验
```

**使用示例** ：

```
场景：老板说"我们要做 AI 功能"

调用 opportunity-solution-tree：
1. 期望结果：提升用户留存率 20%
2. 机会探索：
   - 机会 1：用户不知道如何高效使用产品
   - 机会 2：用户遇到问题找不到帮助
   - 机会 3：用户完成关键流程太耗时
3. 方案发散（每个机会 3-5 个方案）
4. 选择 POC：基于影响力/可行性评分
```

### 3.3 prd-development（产品需求文档）

**核心功能** ：将发现阶段的洞察转化为工程可执行的 PRD 文档。

**解决的问题** ：

- 如何写一份工程师能看懂的 PRD？
- 如何避免需求歧义和范围蔓延？
- 如何确保 PRD 是"活文档"而非一次性交付？

**输出结构** ：

```
# [功能名称] PRD

## 1. 执行摘要
- 一句话概述（问题 + 方案 + 影响）

## 2. 问题陈述
- 谁有问题？
- 问题是什么？
- 为什么痛苦？
- 证据（用户原话、数据、调研）

## 3. 目标用户与画像
- 主要画像
- 次要画像
- Jobs-to-be-done

## 4. 战略背景
- 业务目标（OKR）
- 市场机会
- 竞争格局
- 为什么现在做？

## 5. 方案概述
- 高层描述
- 用户流程图/线框图
- 核心功能列表

## 6. 成功指标
- 核心指标
- 次要指标
- 目标值（当前 → 目标）

## 7. 用户故事与需求
- 史诗假设
- 用户故事 + 验收标准
- 边界情况、约束条件

## 8. 不在范围内
- 明确不做的（及原因）

## 9. 依赖与风险
```

**使用示例** ：

```
场景：完成 JTBD 分析后，需要写 PRD 给开发团队

调用 prd-development：
1. 输入：JTBD 文档、用户调研笔记
2. 技能引导你填充每个章节
3. 输出：完整的 PRD 文档，可直接用于开发
```

### 3.4 prioritization-advisor（优先级建议）

**核心功能** ：根据团队阶段和上下文，选择合适的优先级框架。

**解决的问题** ：

- 应该用 RICE 还是 ICE？
- 为什么团队的优先级总达不成共识？
- 如何避免"框架跳跃"（频繁换方法）？

**推荐的框架** ：

| 框架 | 适用场景 | 需要数据 |
| --- | --- | --- |
| RICE | 数据驱动团队，有明确指标 | 高 |
| ICE | 快速决策，早期产品 | 低 |
| Value/Effort | 快速排序，可视化 | 中 |
| Kano | 区分基础/期望/惊喜功能 | 中 |
| Cost of Delay | 时间敏感功能 | 中 |
| MoSCoW | 强制取舍，版本规划 | 低 |

**使用示例** ：

```
场景：团队在优先级上争论不休

调用 prioritization-advisor：
1. 技能问你一系列问题（团队规模、数据可用性、决策风格等）
2. 推荐最适合的框架
3. 提供实施步骤和模板
```

### 3.5 user-story（用户故事）

**核心功能** ：将需求转化为开发可执行的用户故事卡片。

**解决的问题** ：

- 如何写清晰的用户故事？
- 验收标准怎么写？
- 如何避免故事过大或过小？

**输出格式** ：

```
### 用户故事 [ID]

#### 用例（Mike Cohn 格式）:
- **作为** [用户角色]
- **我想要** [执行的动作]
- **以便于** [期望的结果/价值]

#### 验收标准（Gherkin 格式）:
- **场景**: [场景描述]
- **给定**: [前提条件]
- **当**: [触发事件]
- **那么**: [期望结果]
```

**使用示例** ：

```
场景：PRD 中有一个功能"自动发送付款提醒"

调用 user-story：
输入：功能描述、目标用户
输出：
- 作为 自由职业者
- 我想要 设置自动催款规则
- 以便于 不用手动追客户付款

验收标准：
- 给定 用户设置了催款规则
- 当 发票到期前 3 天
- 那么 系统自动发送催款邮件
```

## 4\. 技能协作工作流

### 4.1 标准产品开发生命周期

```
┌────────────────────────────────────────────────────────────────────┐
│                         完整工作流示例                              │
│                    做一个"自动催款"功能                             │
└────────────────────────────────────────────────────────────────────┘

阶段 1: 发现 (Discovery)
════════════════════════════════════════════════════════════════════
1. proto-persona
   → 定义目标用户：自由职业者（设计师/开发者）
   
2. jobs-to-be-done
   → 发现真实需求：不是"更快开票"，而是"别耽误收款"
   
3. customer-journey-map
   → 绘制旅程：发现"催款"环节最痛苦（平均延迟 15 天）
   
4. tam-sam-som-calculator
   → 评估市场：自由职业者发票工具市场约 50 亿
   
5. discovery-interview-prep + discovery-process
   → 访谈 10 个用户，验证假设

产出：用户洞察文档 + 机会评估报告
```

## 5\. 完整案例演示

### 案例背景

**公司** ：一款面向自由职业者的在线发票 SaaS **问题** ：用户流失率高，老板要求"提升用户体验" **你的角色** ：产品经理

---

### 第 1 步：理解用户（jobs-to-be-done）

**调用技能** ： `jobs-to-be-done`

**输入** ：

- 产品类型：在线发票工具
- 目标用户：自由职业者（设计师、开发者、顾问）
- 表面问题："用户说开票太麻烦"

**输出** （关键洞察）：

```
## Jobs-to-be-Done 分析

### Customer Jobs
#### Functional:
- 月底 2 小时内搞定所有客户的发票
- 跟踪谁付了钱、谁还欠着
- 报税时能快速找到历史记录

#### Social:
- 让客户觉得我是正规公司，不是路边接私活的
- 看起来像有财务团队的专业人士

#### Emotional:
- 别再为发票这种破事焦虑
- 专心做项目，别被行政工作打扰

### Pains
#### Challenges:
- 客户总说"发票没收到"，其实是自己弄丢了
- 不同客户要不同格式的发票
- 记不住谁付了钱

#### Costliness:
- 每月花 6-8 小时折腾发票，时值 3000 元
- 因为发票问题晚收款，平均延迟 15 天

### Gains
#### Expectations:
- 开票时自动填充客户信息
- 一键催款，生成礼貌的提醒邮件

#### Life Improvement:
- 月底不再焦虑，能安心陪家人
- 收款更快，现金流更稳，敢接大项目
```

**洞察** ：

> 用户说的"开票麻烦"，真实意思是"从完工到收款的整个流程太折腾"。真正的机会不是"更快开票"，而是 **自动催款 + 收款跟踪** 。

---

### 第 2 步：探索方案（opportunity-solution-tree）

**调用技能** ： `opportunity-solution-tree`

**输入** ：

- 期望结果：提升用户留存率 20%
- 来自 JTBD 的洞察

**输出** ：

```
提升留存率 20%
                           │
           ┌───────────────┼───────────────┐
           │               │               │
    忘记催款          客户弄丢         对账麻烦
   (平均延迟 15 天)      发票          耗时 3 小时/月
       │                 │               │
    ┌──┴──┐           ┌──┴──┐        ┌──┴──┐
    │     │           │     │        │     │
  自动  模板  人工   自助  邮件   自动  导出  人工
  提醒  消息  提醒   查询  重发   对账  Excel  核对
    │                 │               │
  实验                实验            实验
 A/B 测试           可用性测试      时间追踪
```

**决策** ：

- 选择 POC：自动提醒（影响力最高，可行性中等）

---

### 第 3 步：确定优先级（prioritization-advisor）

**调用技能** ： `prioritization-advisor`

**输入** ：

- 团队规模：5 人（2 开发、1 设计、1 产品、1 运营）
- 数据可用性：有基础指标（活跃、留存、收款周期）
- 决策风格：数据驱动

**输出** ：

```
推荐框架：RICE

评分结果：
1. 自动催款提醒    RICE = 45 (Reach=80%, Impact=3, Confidence=80%, Effort=4 周)
2. 发票自助查询    RICE = 32
3. 自动对账        RICE = 28

建议：先做自动催款提醒
```

---

### 第 4 步：写 PRD（prd-development）

**调用技能** ： `prd-development`

**输入** ：

- JTBD 文档
- OST 分析结果
- 优先级评分

**输出** （PRD 核心章节）：

```
# 自动催款功能 PRD

## 1. 执行摘要
自由职业者平均晚收款 15 天，影响现金流。自动催款功能可在发票到期前自动发送提醒邮件，
目标将收款周期缩短 40%，提升用户留存率 20%。

## 2. 问题陈述
- 谁：自由职业者（设计师、开发者）
- 问题：忘记催款、不好意思催款、催了没效果
- 证据：访谈中 8/10 用户提到"催款尴尬"，平均延迟 15 天

## 3. 目标用户
- 主要：月收入 2 万 + 的自由职业者
- JTBD："别让我为发票焦虑，专心做项目"

## 6. 成功指标
- 核心指标：平均收款周期（当前 25 天 → 目标 15 天）
- 次要指标：催款邮件打开率 (>40%)、续费率 (+20%)

## 7. 用户故事
### 故事 1：设置催款规则
- 作为 自由职业者
- 我想要 设置自动催款规则
- 以便于 不用手动追客户付款

验收标准:
- 给定 用户进入催款设置页面
- 当 用户选择"到期前 3 天发送"
- 那么 系统保存规则并显示确认

### 故事 2：发送催款邮件
- 作为 系统
- 我想要 自动发送催款邮件
- 以便于 提醒客户付款

...
```

---

### 第 5 步：拆故事（user-story + user-story-splitting）

**调用技能** ： `user-story` + `user-story-splitting`

**输出** ：

```
## 迭代 1（MVP）
1. 设置催款规则（开关 + 提前天数）
2. 定时发送催款邮件（默认模板）

## 迭代 2
3. 自定义催款模板
4. 催款历史记录

## 迭代 3
5. 多渠道催款（邮件 + 短信）
6. 智能催款（根据客户行为调整）
```

---

### 第 6 步：画故事板（storyboard）

**调用技能** ： `storyboard`

**输出** ：关键界面的用户流程草图

```
[设置页面] → [规则配置] → [确认成功] → [邮件预览] → [发送记录]
```

---

### 第 7 步：验证结果（business-health-diagnostic）

**调用技能** ： `business-health-diagnostic`

**上线 6 周后** ：

```
## 业务健康度报告

### 核心指标
- 平均收款周期：25 天 → 16 天 (✅ 达成)
- 催款邮件打开率：52% (✅ 超预期)
- 续费率：+18% (接近目标 20%)

### 用户反馈
- "终于不用尴尬地催款了"
- "每月省下至少 4 小时"

### 建议
- 继续迭代：增加短信催款
- 探索：自动对账功能（用户需求上升）
```

**使用的技能** （按顺序）：

1. `jobs-to-be-done` → 理解真实需求

- 续费率提升 18%
- 用户满意度显著提升

### 6.4 最佳实践

#### ✅ 应该做的

1. **先理解问题，再跳方案**
- 先用 jobs-to-be-done，再用 opportunity-solution-tree
	- 避免直接写 PRD
3. **文档是活的，不是交付物**
- PRD、用户故事都是"活文档"
	- 随着认知更新而更新
5. **技能是框架，不是答案**
- 技能帮你结构化思考
	- 真正的答案来自用户调研和数据
7. **组合使用，效果最佳**
- 单个技能有用，组合使用威力更大
	- 参考"技能协作工作流"

#### ❌ 应该避免的

1. **跳过发现阶段**
- 错误：直接写 PRD
	- 正确：先做 JTBD 分析
3. **把技能当 checklist**
- 错误：机械地填充模板
	- 正确：理解背后的思考框架
5. **一次性用所有技能**
- 错误：每个项目都用 46 个技能
	- 正确：根据项目阶段选择
7. **忽视验证环节**
- 错误：功能上线就结束
	- 正确：用 business-health-diagnostic 验证

## 7\. 常见问题

### Q1: 这些技能适合什么类型的产品？

**A**: 主要面向：

- ✅ SaaS 产品（B2B/B2C）
- ✅ 互联网产品（App、Web）
- ✅ 数字化转型项目
- ⚠️ 硬件产品（部分技能适用，需调整）
- ❌ 纯内容产品（如博客、视频）

### Q2: 小团队/个人开发者需要用这么多技能吗？

**A**: 不需要全部。建议：

- **个人开发者** ：jobs-to-be-done + user-story + prd-development（3 个核心）
- **小团队（<10 人）** ：+ opportunity-solution-tree + prioritization-advisor（5 个）
- **中型团队** ：根据项目需要灵活组合

### Q3: 这些技能和敏捷开发是什么关系？

**A**: 互补关系：

```
产品技能          敏捷开发
─────────────────────────────
发现需求    →     产品 Backlog
写 PRD      →     Sprint 规划
用户故事    →     迭代开发
验证结果    →     Sprint 回顾
```

### Q4: 技能输出的文档可以直接用吗？

**A**: 可以，但建议：

1. 技能输出的是 **框架和初稿**
2. 需要结合具体业务填充细节
3. 和团队 review 后定稿

### Q5: 如何评估这些技能的效果？

**A**: 看三个指标：

1. **需求准确性** ：上线后是否解决了真实问题？
2. **团队效率** ：沟通成本是否降低？
3. **业务结果** ：核心指标是否提升？

**A**: 是的。技能来源于：

- 经典产品管理理论（JTBD、OST 等）

- 社区反馈
