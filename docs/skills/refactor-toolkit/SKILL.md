# 重构技能包

> 核心原则：外科手术式修改，只碰非碰不可的地方。

## 触发条件

当用户提到以下关键词时自动激活：
- "重构"、"迁移"、"改造"、"升级"
- "Express → Hono"、"callback → async/await"、"JS → TS"
- "代码规范化"、"统一风格"

---

## 重构方法论概览

本技能包整合三种方法论：

| 方法论 | 来源 | 核心思想 |
|--------|------|----------|
| 经典重构 | Martin Fowler | 小步前进、测试先行、保持行为不变 |
| AI 重构 | Karpathy 四原则 | 外科手术式修改、目标驱动 |
| 渐进式重构 | 阿里团队实践 | 绞杀植物模式、融合策略 |

---

## 阶段零：重构决策

**铁律：先判断是否需要重构，再决定怎么重构。**

### Step 0.1: 识别代码坏味道

加载 `references/code-smells.md`，检查是否存在以下问题：

| 坏味道 | 症状 | 是否需要重构 |
|--------|------|--------------|
| 重复代码 | 同样逻辑出现多次 | 是 |
| 过长函数 | 函数超过 50 行 | 是 |
| 过大类 | 类超过 500 行 | 是 |
| 过长参数列表 | 参数超过 4 个 | 是 |
| 发散式变化 | 一个类因多种原因变化 | 是 |
| 霰弹式修改 | 一个变化要改多个类 | 是 |

### Step 0.2: 重构风险评估

| 风险等级 | 条件 | 测试要求 | 审批要求 |
|----------|------|----------|----------|
| 低 | 单文件、逻辑简单 | 有测试 | 无 |
| 中 | 多文件、逻辑复杂 | 80%+ 覆盖 | 用户同意 |
| 高 | 核心模块、数据变更 | 100% 覆盖 | 需评审 |
| 极高 | 框架迁移、数据库变更 | 全量回归 + 压测 | 架构师审批 |

### Step 0.3: 选择重构策略

根据场景选择：

| 场景 | 推荐策略 | 详细指南 |
|------|----------|----------|
| 小范围优化 | 童子军规则 | 直接执行 |
| 框架迁移 | 渐进式迁移 + API 映射表 | `references/common-scenarios.md` |
| 代码风格统一 | 自动化工具优先 | ESLint + Prettier |
| 遗留代码 | 绞杀植物模式 | 本文档阶段三 |
| 大规模重构 | Wave 机制 + Agent Teams | 本文档阶段三 |

## 阶段一：代码库理解（必须先做）

**铁律：不理解现有代码，不准开始重构。**

### Step 1.1: 探索项目结构

执行以下操作：

1. 读取 `package.json` 了解依赖和技术栈
2. 使用 Glob 扫描目录结构
3. 使用 Grep 搜索关键模式和反模式
4. 读取入口文件理解应用架构

**输出：** 项目结构摘要，包含：
- 技术栈清单
- 主要模块
- 依赖关系
- 测试覆盖情况

### Step 1.2: 提取现有规范

从现有代码中提取：
- 命名规范（变量、函数、文件）
- 代码风格（缩进、格式化）
- 架构模式（分层、模块划分）
- 现有约定和惯例

**输出：** `.claude/rules/existing-patterns.md`

### Step 1.3: 识别重构范围

询问用户：
```
我已经分析了代码库，发现以下可重构点：

| 模块 | 问题 | 风险 |
|------|------|------|
| ... | ... | ... |

请确认：
1. 哪些模块需要重构？
2. 哪些模块不能动？
3. 重构的优先级？
```

**铁律：没有计划，不准动手。**

|--------|----------|----------|

### Wave 1（并行）
- agent-1：文件所有权 [目录]

### Wave 2（依赖 Wave 1）

### Step 2.2: 阿里融合策略

对于复杂重构，采用阿里团队的融合策略：

```
1. Rules 约束
   └─ 固化项目规范、代码风格

2. 技术方案模板（轻量级）
   └─ 30 分钟完成

3. Agentic Coding
   └─ AI 按方案实现

4. AI 汇总文档
   └─ 保持同步
```

### Step 2.3: 用户确认

展示计划后询问：
```
重构计划已生成，请确认：
1. 范围是否正确？
2. 优先级是否合理？
3. 有没有遗漏的风险点？

确认后我将开始执行。
```

## 阶段三：执行重构

**铁律：遵循重构核心原则。**

### 核心原则

#### 原则一：Martin Fowler 经典原则

| 原则 | 说明 |
|------|------|
| 小步前进 | 每次只做一个小改动，改完测试 |
| 保持行为不变 | 重构不改变功能，只改变结构 |
| 测试先行 | 有测试保护才能安全重构 |
| 持续集成 | 重构是日常活动，不是专项任务 |

**重构节奏：**
```
1. 识别坏味道
2. 添加测试（如果没有）
3. 应用重构手法
4. 运行测试验证
5. 提交代码
```

#### 原则二：Karpathy 四原则（AI 重构核心）

| 原则 | 说明 | AI 常见违反 |
|------|------|-------------|
| 编码前先思考 | 不确定就问，不要猜 | 直接假设，闷头干 |
| 简单优先 | 只写最少代码 | 过度抽象，写太多 |
| 外科手术式修改 | 只碰必要的地方 | 顺便优化其他代码 |
| 目标驱动执行 | 给成功标准让它自己跑 | 没目标就开始干 |

**外科手术式修改详解：**
- 加载 `references/surgical-modification-rules.md`

```
✅ 正确做法：
- 只修改任务范围内的代码
- 保持现有风格一致
- 改完清理多余的 import/变量

❌ 错误做法：
- 顺便"优化"旁边的代码
- 改注释、改命名
- 重构没坏的东西
```

### 重构手法

加载 `references/refactor-techniques.md`，根据需要选择：

| 手法 | 用途 |
|------|------|
| 提取方法 | 将代码片段变成独立方法 |
| 内联方法 | 将方法体嵌入调用处 |
| 移动方法 | 将方法移到更合适的类 |
| 提取类 | 将部分职责提取为新类 |
| 卫语句 | 用 return 替代嵌套 if |

### 执行模式

根据重构规模选择：

**小规模重构（1-5 个文件）：**
- 直接执行，每改一个文件运行测试
- 遵循小步前进原则

**中规模重构（5-20 个文件）：**
- 使用 Superpowers `writing-plans` 拆任务
- 使用 Superpowers `TDD` 确保质量
- 每 3 个任务暂停汇报

**大规模重构（20+ 个文件）：**

**方法一：Wave 机制 + Agent Teams**
```
Wave 1（并行执行）：
├─ Agent A：负责模块 X（文件所有权：src/x/）
├─ Agent B：负责模块 Y（文件所有权：src/y/）
└─ 独立任务，互不依赖

Wave 2（依赖 Wave 1）：
└─ Agent C：负责集成
```

**方法二：绞杀植物模式（遗留系统）**
```
新功能用新架构
老功能逐步迁移
不大爆炸式重写
保持系统始终可用
```

## 阶段四：验证与收尾

**铁律：没有跑验证命令，不准说完成。**

### Step 4.1: 运行测试

```bash
# 必须运行并看到输出
npm test
```

### Step 4.2: 行为对比验证

对于高风险重构，必须验证行为一致性：

```
1. 对比重构前后 API 返回值
2. 对比重构前后日志输出
3. 对比重构前后性能指标
```

### Step 4.3: 检查清单

加载 `references/refactor-checklist.md`

```markdown
## 重构完成检查清单

### 重构前
- [ ] 理解现有代码逻辑
- [ ] 确认有测试覆盖
- [ ] 创建备份分支

### 重构中
- [ ] 只修改计划内的代码
- [ ] 保持现有风格一致
- [ ] 每次改动后运行测试

### 重构后
- [ ] 所有测试通过
- [ ] 行为与重构前一致
- [ ] 没有多余代码残留
```

### Step 4.4: 生成重构报告

使用 `assets/refactor-report-template.md` 生成报告。

## 禁止事项

以下行为绝对禁止：

| 禁止 | 原因 |
|------|------|
| ❌ 无测试就重构核心代码 | 无法验证行为正确 |
| ❌ 重构同时加新功能 | 无法区分 bug 来源 |
| ❌ 大爆炸式重写 | 无法定位问题 |
| ❌ 不理解代码就动手 | 可能破坏现有逻辑 |
| ❌ 改变 API 行为 | 影响调用方 |
| ❌ 顺便优化其他代码 | 范围不可控 |

## 常见重构场景

详见 `references/common-scenarios.md`

### 场景一：框架迁移

**方法论：渐进式迁移**

1. 建立双跑（新旧框架并行）
2. 模块迁移（非核心模块开始）
3. 全量切换（监控 + 回滚方案）

### 场景二：遗留代码重构

**方法论：绞杀植物模式**

```
新功能 → 新架构
老功能 → 逐步迁移
不进行 → 大爆炸式重写
```

### 场景三：大规模重构

**方法论：Wave 机制**

- Wave 1：并行执行独立任务
- Wave 2：执行依赖任务
- 每个 Wave 完成后验证
