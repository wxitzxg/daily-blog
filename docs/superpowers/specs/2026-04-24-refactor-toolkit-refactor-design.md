# refactor-toolkit 拆分设计

> **目标**：将单一的重构技能包拆分为6个独立技能，采用主从结构，支持主动发现和直接重构两种入口模式。

---

## 一、技能结构

```
refactor-toolkit（主技能，编排器）
├─ refactor-audit（审计）
├─ refactor-decide（决策）
├─ refactor-design（方案设计）
├─ refactor-review（方案审查）
├─ refactor-plan（实现计划）
├─ refactor-execute（执行）
└─ refactor-verify（验证）
```

**共7个技能，主从结构。**

---

## 二、各技能职责

| 技能 | 职责 | 输入 | 输出 |
|------|------|------|------|
| **audit** | 项目结构分析 + 坏味道识别 + 测试覆盖检查 + 场景推荐 + 依赖顺序 | 项目路径 | 审计报告 |
| **decide** | 场景确认 + 风险评估 + 方法论选择 | 用户请求/审计结果 | 决策报告 |
| **design** | 架构设计 + 接缝识别 + API映射/Wave划分 | 决策报告 | 重构方案 |
| **review** | 方法论审核 + 范围审核 + 风险审核 + 接缝审核 + 场景特定审核 | 重构方案 | 审查报告 |
| **plan** | 任务拆解 + 步骤定义 + 执行准备 | 重构方案 | 实现计划 |
| **execute** | 外科手术式修改 + 小步循环 | 实现计划 | 代码变更 |
| **verify** | 测试验证 + 行为对比 + 报告生成 | 代码变更 | 验证报告 |

---

## 三、技能详细设计

### 3.1 refactor-audit（审计）

**职责**：深度扫描项目，主动发现重构机会。

**流程**：
```
1. 分析项目结构
   ├─ 读取 package.json/依赖配置
   ├─ 扫描目录结构
   └─ 识别主要模块

2. 识别代码坏味道
   ├─ 重复代码
   ├─ 过长函数（>50行）
   ├─ 过大类（>500行）
   ├─ 过长参数列表（>4个）
   ├─ 发散式变化
   └─ 霰弹式修改

3. 检查测试覆盖
   ├─ 统计测试覆盖率
   └─ 识别测试盲区

4. 推荐重构场景
   ├─ 根据坏味道匹配场景
   ├─ 标注依赖关系
   └─ 建议执行顺序

5. 输出审计报告
```

**输出格式**：
```markdown
# 审计报告

## 项目概况
- 技术栈：[...]
- 主要模块：[...]
- 测试覆盖率：XX%

## 发现的问题
| 模块 | 坏味道 | 严重程度 |
|------|--------|----------|
| ... | ... | ... |

## 推荐重构场景
| 场景 | 优先级 | 依赖 |
|------|--------|------|
| 1. 代码风格统一 | P0 | 无 |
| 2. 技术栈升级 | P1 | 依赖1完成 |
| 3. 框架迁移 | P2 | 依赖1、2完成 |
```

---

### 3.2 refactor-decide（决策）

**职责**：确认重构方向，评估风险，选择方法论。

**流程**：
```
1. 场景确认
   ├─ 用户明确场景 → 直接确认
   └─ 用户未明确 → 根据描述推断

2. 风险评估
   ├─ 低：单文件、逻辑简单
   ├─ 中：多文件、逻辑复杂
   ├─ 高：核心模块、框架迁移
   └─ 极高：数据库变更、架构重写

3. 方法论选择
   ├─ 经典重构（Martin Fowler）：小步前进、测试先行
   ├─ AI重构（Karpathy四原则）：外科手术式、目标驱动
   └─ 渐进式重构（阿里实践）：绞杀植物模式、融合策略

4. 流程建议
   ├─ 低风险 → 简化流程
   └─ 高风险 → 完整流程

5. 输出决策报告
```

**方法论与场景对应**：

| 场景 | 风险 | 方法论 | 流程 |
|------|------|--------|------|
| 小范围优化 | 低 | 童子军规则 | 简化 |
| 代码风格统一 | 低 | ESLint/Prettier | 简化 |
| 技术栈升级 | 中 | 分阶段迁移 | 完整 |
| 框架迁移 | 高 | 渐进式迁移 | 完整 |
| 遗留代码重构 | 高 | 绞杀植物模式 | 完整 |
| 大规模重构 | 高 | Wave机制 | 完整 |

---

### 3.3 refactor-design（方案设计）

**职责**：设计具体重构方案，识别安全修改点。

**流程**：
```
1. 架构设计
   ├─ 确定重构目标架构
   └─ 规划模块边界

2. 接缝识别
   ├─ 识别可安全修改的入口点
   ├─ 分析依赖关系
   └─ 确定修改顺序

3. 具体设计（根据场景）
   ├─ 框架迁移 → API映射表
   ├─ 大规模重构 → Wave划分
   └─ 遗留代码 → 双跑设计

4. 输出重构方案
```

**接缝（Seam）**：
> 一个可以安全修改的地方，不会影响调用方。

**输出格式**：
```markdown
# 重构方案

## 目标架构
[架构描述/图示]

## 接缝清单
| 接缝 | 位置 | 修改类型 |
|------|------|----------|
| ... | ... | ... |

## API映射表（框架迁移）
| 源 API | 目标 API | 注意事项 |
|--------|----------|----------|
| ... | ... | ... |

## Wave划分（大规模重构）
- Wave 1：[模块A] + [模块B]（并行）
- Wave 2：[模块C]（依赖Wave 1）
```

---

### 3.4 refactor-review（方案审查）

**职责**：自动全方位审查重构方案，发现问题并提出改进建议。

**流程**：
```
1. 方法论审核
   ├─ 方法论是否适合当前场景？
   └─ 是否有更优的方法论可选？

2. 范围审核
   ├─ 重构范围是否合理？
   ├─ 是否有遗漏的模块？
   └─ 是否有不必要的重构？

3. 风险审核
   ├─ 风险等级评估是否准确？
   ├─ 是否有未识别的风险？
   └─ 回滚方案是否可行？

4. 接缝审核
   ├─ 接缝是否可以安全修改？
   └─ 是否有遗漏的接缝？

5. 场景特定审核
   ├─ 框架迁移：API映射表是否完整？行为差异是否识别？
   ├─ 大规模重构：Wave划分是否合理？文件所有权是否清晰？
   └─ 遗留代码：特性测试是否覆盖关键行为？

6. 输出审查报告
   ├─ 通过 / 需修改
   ├─ 问题清单
   └─ 改进建议
```

**输出格式**：
```markdown
# 方案审查报告

## 审查结果：通过 / 需修改

## 问题清单
| # | 类别 | 问题描述 | 严重程度 | 改进建议 |
|---|------|----------|----------|----------|
| 1 | 范围 | 模块X未纳入范围 | 高 | 建议添加 |
| 2 | 接缝 | 接缝Y依赖未分析 | 中 | 补充依赖分析 |

## 改进建议
1. ...
2. ...
```

**审查结果处理**：
- **通过**：自动进入 plan 阶段
- **需修改**：返回 design 阶段修改方案

---

### 3.5 refactor-plan（实现计划）

**职责**：将方案拆解为可执行的小步骤，准备执行环境。

**流程**：
```
1. 任务拆解
   ├─ 每个任务 2-5 分钟可完成
   └─ 任务间依赖关系清晰

2. 步骤定义
   ├─ 具体代码变更
   ├─ 测试命令
   └─ 预期结果

3. 执行准备
   ├─ 创建重构分支
   ├─ 打 tag 标记起点
   └─ 确认测试可运行

4. 输出实现计划
```

**输出格式**：
```markdown
# 实现计划

## 准备工作
- [ ] 创建分支：feature/xxx
- [ ] 打 tag：before-refactor-xxx
- [ ] 确认测试通过

## 任务清单

### Task 1: [任务名称]
**文件**：
- 修改：`path/to/file.ts`

**步骤**：
- [ ] Step 1: 写测试
- [ ] Step 2: 运行测试确认失败
- [ ] Step 3: 实现代码
- [ ] Step 4: 运行测试确认通过
- [ ] Step 5: 提交
```

---

### 3.6 refactor-execute（执行）

**职责**：按计划执行重构，遵循外科手术式修改原则。

**核心原则**：
```
1. 只碰必要的地方
2. 保持现有风格一致
3. 每次小改动后运行测试
4. 不顺便优化其他代码
```

**执行模式**：

| 规模 | 模式 |
|------|------|
| 小（1-5文件） | 直接执行，每改一个文件运行测试 |
| 中（5-20文件） | 使用 writing-plans 拆任务，TDD 确保质量 |
| 大（20+文件） | Wave 机制，Agent 并行执行 |

**小步循环**：
```
改代码 → 运行测试 → 测试通过 → 提交 → 下一步
         ↓
      测试失败 → 修复 → 重新测试
```

---

### 3.7 refactor-verify（验证）

**职责**：验证重构结果，确保行为一致。

**流程**：
```
1. 运行全量测试
   ├─ 单元测试
   ├─ 集成测试
   └─ E2E测试

2. 行为对比（高风险重构）
   ├─ API 返回值对比
   ├─ 日志输出对比
   └─ 性能指标对比

3. 代码质量检查
   ├─ ESLint/Prettier
   ├─ 类型检查
   └─ 无 console.log 残留

4. 生成验证报告
```

**输出格式**：
```markdown
# 验证报告

## 测试结果
- 单元测试：XX 通过
- 集成测试：XX 通过
- 覆盖率：XX%

## 行为对比
| 检查项 | 结果 |
|--------|------|
| API行为一致 | ✅ |
| 性能无明显下降 | ✅ |

## 变更统计
- 文件数：XX
- 新增行：XX
- 删除行：XX
```

## 四、完整流程

### 4.1 入口一：主动发现模式

```
用户："帮我看看哪些需要重构"
    ↓
refactor-audit
    ↓
显示审计报告（场景推荐 + 优先级 + 依赖）
    ↓
用户选择场景
    ↓
refactor-decide → design → review → plan → execute → verify
```

### 4.2 入口二：直接重构模式（完整流程）

```
用户："把Express迁移到Hono"
    ↓
refactor-decide
    ├─ 场景：框架迁移
    ├─ 风险：高
    └─ 方法论：渐进式迁移
    ↓
【确认点1】是否继续？
    ↓ 是
refactor-design
    ├─ 接缝识别
    └─ API映射表
    ↓
refactor-review（自动审查）
    ├─ 通过 → 继续
    └─ 需修改 → 返回 design
    ↓ 通过
refactor-plan
    ├─ 任务拆解
    └─ 创建分支/tag
    ↓
refactor-execute
    └─ 小步循环执行
    ↓
refactor-verify
    └─ 输出验证报告
```

### 4.3 简化流程（低风险场景）

```
用户："把callback改成async/await"
    ↓
refactor-decide
    ├─ 场景：小范围优化
    ├─ 风险：低
    └─ 流程建议：简化
    ↓
【确认点1】是否继续？
    ↓ 是
refactor-execute
    ↓
refactor-verify
```

## 五、确认点设计

| # | 确认点 | 阶段 | 审核内容 |
|---|--------|------|----------|
| 1 | 是否继续？ | decide 后 | 场景 + 风险 + 方法论确认 |

**方案审查由 refactor-review 技能自动完成**，审查结果：
- **通过**：自动进入 plan 阶段
- **需修改**：返回 design 阶段修改方案

## 六、主技能编排逻辑

```python
def refactor_toolkit(user_request):
    # 判断入口模式
    if is_audit_request(user_request):
        # 主动发现模式
        audit_result = refactor_audit(project_path)
        display(audit_result)
        selected = ask_user_to_select(audit_result.scenarios)
        user_request = selected

    # 决策阶段
    decision = refactor_decide(user_request)
    if not confirm("是否继续？"):  # 确认点1
        return

    # 根据场景选择流程
    if decision.risk in ['低']:
        # 简化流程
        refactor_execute()
        refactor_verify()
    else:
        # 完整流程
        design = refactor_design()

        # 自动审查方案
        while True:
            review_result = refactor_review(design)
            if review_result.passed:
                break
            # 需修改：返回 design 修改
            design = refactor_design(review_result.issues)

        refactor_plan()
        refactor_execute()
        refactor_verify()
```
